# Slides create — 通常の入口

ユーザーはこのスキルだけを指定すればよい。内部スキルは必要なときに自分で読み、工程を引き継ぐ。
別のスキルを順番に起動するようユーザーへ求めない。

- 新規作成・論理や配置の見直し：この文書 → [slides-layout](../slides-layout/SKILL.md)
- 内容入り資料の生成後、既存資料の点検：[slides-review](../slides-review/SKILL.md)
- 修正の反映：[slides-tune](../slides-tune/SKILL.md)
- 明示された過去資料フォルダから配置傾向を学ぶ場合だけ：[slides-analyze](../slides-analyze/SKILL.md)

小さな誤字修正などは指定箇所を直し、再描画して確認する。既存の論理構造を毎回作り直さない。
配置案だけの依頼なら配置案まで、完成までの依頼なら制作・検証まで続ける。
ユーザーが明示的に承認を求めた工程以外で、承認待ちを新設しない。

## 文章を先に決める

新規制作や構成変更では、まず `docs/MESSAGE_FIRST.md` を読む。資料の用途、聴衆、
発表時間、用紙・投影寸法、印刷倍率、文字サイズを確認し、提供済みの条件は引き継ぐ。

1. 最新の原稿・資料から、発信したいメッセージを1〜2文にする。
2. その主張に至る短い説明文を書く。先に導入した概念を受けて、後の概念・主張が
   必要になる順序にする。分類見出しを並べただけで済ませない。
3. 各段落の主張、前提となる概念、導入する概念、裏付ける図表を `story.yaml` に記録する。
   用語の定義、提案全体と要素技術の関係、実験が何を確かめるかを文章で確認する。
4. `structured-slide-creator story check story.yaml` と `story md` で順序・参照と実際の説明文を確認する。
   機械検査の成功を、文章の論理や研究内容の正しさの保証としない。

数値・成果・技術的な新規性を創作しない。目的、実施内容、得られた結果、今後の展開を
自然な文章で書き分ける。不要な責任回避文を発表資料へ差し込まない。

## 配置を決めてから内容を入れる

内部の `slides-layout` へ、上の文章・概念の順序・図表一覧・制作条件を渡す。
Astraが利用できる環境では、新しい配置の設計を依頼する。モデル指定がある場合は実際の
指定モデルを使い、利用できなければ代替と確認範囲を明示する。利用できるだけでは
外部サービスへの送信や公開の許可にはならない。

配置案では各領域の役割、主張・図表との対応、読む順序、面積配分を示す。
図・本文を入れる前の編集可能なワイヤフレームを作り、メッセージの重要度が配置に
表れているか確認する。実験に常に半分の面積を割くなど、固定比率を一般則にしない。

内容を入れる際は、提供された論文の図表をまず活用する。日本語化やラベル調整で足りる図を
描き直さない。新しい図は、未導入の用語や仕組みを理解するために必要な場合に追加する。
各図の前提・説明・結論を近接させ、同じ概念には同じ名前・色・記号を使う。
参考デザイン資料の別研究の内容と、ユーザーが制作素材として提供した原稿・図表を区別する。

## 制作と確認

`docs/HELPERS.md` を参照し、配置と内容をplanへ反映する。分割は `draw_split_layout()`、
表は `make_table()` など既存ヘルパーを使う。新しい配置はレイアウト計画に明示し、
共通テーマの下限を黙って下げない。文字が入らない場合は説明・配置・分割を見直す。
16pt、白抜き帯、A3など今回の資料固有の指定を、別の資料へ無条件に適用しない。

`structured-slide-creator plan check <plan>` → `structured-slide-creator build <plan> --out <deck.pptx>` の後、
内部の `slides-review` に従い、生成スクリプトと実際の描画画像を両方確認する。
この環境でAstraが使える場合は最終画像の確認を依頼する。使っていないモデルによる確認を装わない。
配置案の確認は内容入り完成版の確認を兼ねない。変更後は新しいPPTXから再描画する。

`custom_script` は内容を確認したローカルスクリプトだけを使う。
最終成果物は全ページを再ビルドする。`--only` は既存ページの部分置換ではない。
