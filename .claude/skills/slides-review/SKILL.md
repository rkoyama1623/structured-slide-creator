# Slides review — 内部の確認工程

通常の入口は [slides-create](../slides-create/SKILL.md)。ユーザーに追加のスキル指定を求めない。
ヘルパーAPIは `docs/HELPERS.md` を参照する。

`structured-slide-creator review <pptx> --out <report-directory> --sources <plan> <script> ...` を実行する。
実際にある生成元だけを指定し、他フォルダを推測して走査しない。
テーマは隣接manifestから自動取得される。外部PPTXには `--theme` を明示する。

生成元を読んで数値、図表の由来と引用、概念の順序、宣言された寸法・文字サイズ、
編集可能性を確認する。ハッシュを採取しただけでソース確認済みとはしない。

次に実際の描画画像を表示する。この環境でAstraが利用可能なら画像の確認を依頼する。
全体に加え、主要図・小さいラベル・結果・フッターなどを必要に応じて拡大して確認する。
メッセージから読む順序、未導入の用語、本文と図の論証関係、強調と面積配分も見る。

- `must_fix` を優先する。重なり・整列・文字あふれは推定なので、画像で意図と照合する。
- 画像で文字切れ、図の接続関係、凡例と軸の単位、読み順、余白を確認する。
- レポートのPPTX・画像・生成元のハッシュと、実際に見たページ、指摘、修正結果を残す。
  自動検査や画像出力だけでレビュー担当者の承認を作らない。違う版の画像で完成版を確認したことにしない。
- 配置だけの承認は本文入り完成版を含まない。変更後は新しいPPTXから再描画して確認する。
- LibreOfficeの `fidelity: approximate` はPowerPointの表示一致を保証しない。
- レンダラが無ければ `structured-slide-creator doctor` で診断し、`--no-render` の構造検査を行う。
  画像未確認なのに視覚レビュー済みと報告しない。
- 問題はスライドID・要素・理由・修正案で記録し、内部の `slides-tune` で生成元へ反映する。

既存PowerPointへの手修正はplanの再ビルドで失われる。変更は生成元にも反映し、
`--only` で確認した場合も最終版は全ページを再生成する。
